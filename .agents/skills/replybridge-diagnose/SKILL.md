# ReplyBridge 排障

找出故障发生在哪个环节，用日志、持久化状态或可复现用例支持结论。诊断请求只读；明确要求修复时继续完成范围内修复和验证。普通编辑无需本技能。

## 定位入口

按症状沿“平台读取 → SQLite → 飞书通知 → 引用映射 → 平台写入”检查，不要求遍历全部环节。

| 症状 | 优先查看 |
| --- | --- |
| 漏评论或抓取延迟 | `internal/bili/comments.go`、`internal/youtube/comments.go`、命令入口中的 `nextCommentPollDelay` |
| 通知缺失或积压 | `internal/commentbridge/service.go`、`store.go` 中对应 outbox 和 `internal/feishu/client.go` |
| 引用回复或点赞异常 | `internal/feishu/events.go`、存储层 `AcceptReply` / `AcceptEngagement`、对应平台适配器 |
| 登录失效或二维码异常 | 对应平台 `auth.go` / `oauth.go`、凭据告警和刷新任务 |
| 没有错误告警 | `internal/commentbridge/error_alerts.go`、告警去重状态及飞书发送路径 |

表中代码路径相对于项目根目录。权限、配置与故障操作按需查阅[使用文档](../../../docs/comment-bridge.md)；涉及容器或外挂目录时查阅[部署文档](../../../deploy/comment-bridge/README.md)。

## 证据与判断

- 先确认正在观察的实例、版本、目标账号和时间范围；从当前环境核实，不沿用旧任务的线上状态。只收集判断必需的脱敏信息。
- 复用已部署二进制的 `status --db <已确认的数据库路径>`；当前实现只读打开现有数据库。不要为了诊断启动 `run`、初始化新库或执行迁移。补充 SQL 查询使用只读连接，并按当前 schema 查询。
- 通知数量差异可能来自首次基线、自身回复过滤、分页覆盖范围、夜间降频、B站冷却或尚在消费；结合评论记录、任务状态及多次观察确认，不能直接认定数据丢失。
- 区分平台错误类别：登录失效、读取限流、写操作结果未知和网络失败不能共用自动恢复策略。B站冷却或恢复读取验证期间不尝试回复、点赞，也不重启绕过冷却。
- 检查飞书精确目标群、授权模式、直接 parent 引用和原通知映射。YouTube 的飞书 👍 当前产生手动点赞提示，不代表平台点赞失败。
- `unknown` 可能已在外部成功。先人工核对；仅在获得对应恢复授权且确认未执行后，按使用文档对单个动作恢复。`retry-unknown` 会修改任务状态，属于写操作；不批量重试，不直接改 SQL 伪造成功。

## 修复与完成

修复前追踪相关调用方，在共享根因处修改；复用对应包已有测试，覆盖实际症状及受影响的授权、去重或结果分类。需要真实发送、回复、点赞或扫码验证时，使用本次已授权的目标；缺少授权只暂停该环节，继续本地验证。

交付已确认原因与证据、修复及验证结果、仍未核验的环节。没有发现问题时说明检查范围，不将容器健康、告警消失或单次读取成功当作整个链路恢复。
